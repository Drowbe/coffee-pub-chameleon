# Modules Architecture

**Audience:** developers changing how Coffee Pub Chameleon installs and stores modules.

What an admin does with modules is [userguide-modules](../userguides/userguide-modules.md), and the
routes are [api-modules](../api/api-modules.md). This document is what you can only learn from
`server/modules.js`.

## Model

A module is front-end only. Nothing in a zip is ever run by the server: every file type is allowlisted,
and the zip is read entirely in memory against hard limits before a single byte is written. A module
runs in a sandboxed frame and reaches Chameleon only through a host bridge, so accepting a zip from someone
else is bounded by that sandbox and by the admin's approval, not by trust in the author.

## On disk

Under `DATA_DIR/modules`:

```
registry.json                     what is installed and its state
<id>/versions/<version>/...       the module's files, one folder per version
<id>/data/                        the module's own data, kept across upgrades
<id>/trash/                       what a Clear took, held for its Undo (see "Clear and Undo")
<id>/library/                     a library module's file records (see "Library modules: the Vault")
```

`registry.json` is written by writing a temporary file and renaming it. Each entry holds the active
`version`, the list of installed `versions`, `enabled`, `allSpaces`, `spaces` (`allRooms` and `rooms` before the Names migration's `names-spaces` part), and `approved`, which is
the permissions and hooks the admin agreed to. The manifest is read from the version's own
`module.json` on demand, so the registry cannot drift from the files.

## Display names, icons and words

What a person reads a module called is its **display name** in this environment
(plan-environment-templates, step 2). `store.moduleDisplay(id)` in `server/store.js` resolves it for any module,
installed, bundled or built in: the owner's own (`settings.moduleNames`, `settings.moduleIcons`), else the
template's (step 3), else null, meaning the manifest's own `name` and `icon`. An icon counts only while it can be
drawn (`displayIconIds()`: the environment's plain solid icons, `fa-solid fa-<id>`, and every installed or built-in
module's own icon); one that can't be drawn now is kept as the owner's (`ownDisplayIcon`) and the next one down is
shown. `buildEnvironment()` hands this to the module manager as `modules.displayOf`, and `modules.shownName()`
is what every sentence, notification and activity line uses. `GET /api/modules` keeps `name` and `icon` as the
manifest's and adds `displayName`, `displayIcon`, `ownDisplayName` and `ownDisplayIcon`; the module's own page
gets the display name and icon as `info.module`. The top bar names no module, so a change needs no redraw there.
A module's display name replaces its name only, never a widget's own title. On Manage the owner edits them on the Template tab (one row per module, `#template-module-<id>`); each Modules card shows only "Shown as" with a **Change** link to that row.

The text in a manifest that people read (description, widget title, permission labels, setting labels, help and
options, event and action labels, kind names) may carry the environment's word placeholders (`{space}`,
`{a space}`, ...), and is filled from the environment's words wherever it is sent, so it reads in the owner's
words (see "Words" in [architecture-overview](architecture-overview.md)).

## Reading the zip

`readZip` in `server/modules.js` uses `yauzl` on the uploaded buffer and builds a map of file name to
bytes. It refuses, with a message the admin sees:

- an unsafe path (the library already rejects `..` and absolute paths), or control characters in a name;
- a symbolic link, detected from the entry's Unix mode bits;
- any extension not on the allowlist;
- more than 500 files, a file over 10 MB, or more than 40 MB in total.

Sizes are checked twice: from the entry header before reading, and again on the bytes actually
streamed, because a header can lie. A zip made from a folder, with everything inside one top-level
folder, has that folder stripped when `module.json` is found inside it.

## Manifest validation

`cleanManifest` builds a fresh object from only the fields it knows, so unknown fields cannot reach the
registry, and it checks that each surface entry exists in the zip. It returns the cleaned manifest or
throws a `ModuleError`, which is a `StoreError` and so is turned into a JSON error by the server's
error handler.

Since step 5c of the [Names plan](../plans/plan-names.md), `oldNameIn()` checks the raw manifest first: a module
`scope` of `server` or `room`, a setting's scope, `install.settingsFrom: "server"`, or a permission default keyed
`user` refuses the upload with one sentence naming the new word. The stored `module.json` is the author's
original, so an installed version in the old names is kept and read with `manifest.outdated` set: it counts as
off whatever the registry says (`enabledAll()` and the run routes skip it), `GET /api/modules` shows `outdated`,
`outdatedWhy` and `outdatedVersions`, turning it on or rolling back to such a version answers 409, and
`needsUpdateFor()` keeps off every module that requires one (409 "`<Name>` needs `<Req>`, which needs an update from
its author."). More generally, a module runs only while everything it requires is running, at any depth; the
owner's on or off is kept, so it comes back by itself when its requirement does, and `missing` and `needsUpdate`
on its card say why it isn't running. The registry keeps the owner's own on or off, so an update that fixes the manifest runs as before.
Modules that ship with Chameleon are updated to their new copies on start (see
[architecture-environments](architecture-environments.md), "Bundled modules built for an older version").

A permission may name `replaces`, the key it had in an earlier version; each role's choice for that key in
`settings.roles` is carried over once, at start and after any install, so renaming a permission keeps what owners
chose. Two permissions naming the same old key are refused: `module.json: permission "<second>" replaces "<old>",
which permission "<first>" already replaces`.

## Modules that ship with Chameleon

`server/module-build.js` builds a module's zip from its source folder (`modules/<id>/module.json` and `src/`), inlining the CSS and JS into the pages; `tools/build-module.mjs` uses it to write a zip, and the server uses it to offer the modules in the deployment's own `modules/` folder. `GET /api/modules` compares each bundled version with the installed one (`update` is true when it is newer and not already kept), and `POST /api/modules/bundled/:id/install` builds the zip in memory and passes it to `install()`, so a bundled install or update goes through the same validation, version keeping and approval as an upload: an update that asks for something new is left disabled until approved. An installed copy is updated only when the bundled version is newer, so any change to a bundled module needs a version bump; `tools/check-module-versions.mjs` enforces it against a recorded fingerprint. Only folders directly under `modules/` whose `module.json` id matches the folder name and that have a `src/` are offered, by id, so a request cannot name a path.

## Install, upgrade and rollback

**Stored keys a module renamed.** A manifest's `storage.renamed` (`[{ from, to }]`, key prefixes) makes the server
keep the module's stored keys matching the version running: `server/module-data.js` renames keys starting with
`from` to `to` in every scope: a rename is in effect for every version from the one that introduced it onward, even if later versions stop listing it. While it is in effect, keys still under the old prefix are moved on every start, install, update and rollback; switching to a version older than the one that introduced it moves the keys back (the newest rename first) and drops the record. The registry records each as `renamed: [{ from, to, version, at, kept }]`. A key whose new name is already taken is never overwritten: both are kept (`kept`). The log and the activity list note only keys actually moved and new conflicts. `cleanStorage()` in `server/modules.js` refuses a list that repeats a
`from`, overlaps or would move keys back.

**Bundled modules keep up with the server.** On each start, every module that came with this deployment is updated
to the version the server ships whenever the update asks for nothing new to approve; one that asks for more waits
for an owner, and the installed version keeps running meanwhile. Uploaded modules are never touched. (Since step 7;
before, only an outdated bundled module was updated on start, see [architecture-environments](architecture-environments.md).)

Files are written to a staging folder next to the final location and moved into place with a single
rename, so a failure never leaves a half-installed version. A new module is created disabled. An
upgrade keeps `enabled`, `allSpaces` and `spaces`, then compares what the new manifest asks for with
`approved`; anything new turns `enabled` off. Rollback changes only the active `version` and applies
the same check. After each install, only the newest three versions are kept, never removing the active
one.

## Approval

`pendingFor` returns the permissions, hooks and `refs.consumes` entries in the active manifest that are not in `approved`.
Enabling copies the whole current set into `approved`. That is why an upgrade can quietly gain a
capability only if the admin approves it.

## Uninstall

Removes the `versions` folder and the registry entry. The `data` folder is removed only when asked, so
that reinstalling the same `id` finds its data again.

## Running a module

What an admin does is [userguide-modules](../userguides/userguide-modules.md); what a module author sees is [api-module-sdk](../api/api-module-sdk.md). This is how the pieces fit.

```
 module frame (sandboxed)  <--postMessage-->  host page (module-host.js)  <--HTTP + SSE-->  server
   public/sdk/host.js                          module.js or canvas.js               index.js, modules.js,
                                                                                            module-data.js, module-hooks.js
```

### The dashboard

The spaces page is a `.home` grid: a sticky sidebar, `#dashboard`, on the left and `.home-main` on the right (a `#whos-around` strip, then the space cards); in the narrow layout one column with the main part first. `public/dashboard.js` fills the sidebar with a card for each module with a `surfaces.widget`, listed by `GET /api/modules/widgets` in the order the manifests ask for. A widget is mounted exactly as a module page is (`mountModule` with `scope: 'environment'`, in the page for a bundled module and in a sandboxed frame otherwise), so it uses the same SDK and the same reads across the viewer's spaces (`spaces-data`, checked against the module's read permission in each space). Chameleon knows nothing of what a widget shows. An object a widget opens (`objects.open`) in a space takes the person into that space with only that module open on the canvas: `openInSpace` in `public/space.js` asks the canvas manager (`requestOpen` in `public/canvas.js`) to open just that module and hand it the pointer on the next restore, then joins (or shows the canvas when already in that space). That one-off layout is not remembered as the space's layout until the person opens or closes a module themselves. An object outside a space goes to the module's page, given the pointer in the address (`openRef` in `dashboard.js`); the card's heading links to the module's own page. While the module is part of a shown destination, the heading, `host.page.open` and the tile's own module's objects go to the destination instead (`tileRefTarget()`; see [architecture-navigation](architecture-navigation.md), "Module pages"), and `{ newTab }` on either opens a new tab. Who is around (Chameleon's own, from `/api/presence`) is drawn into the strip. A widget can ask for its module's page at a place in it with `host.page.open(hash)` (the host's `page.open`, answered only by the dashboard), which goes to `/modules/<id>#hash`; the module page hands the hash to the module (`pagehash`, `host.page.onHash`), as it does a pointer. The sidebar stays hidden until it has a card; a guest has no dashboard. A module's build (`server/module-build.js`) writes the widget entry from `src/<id>-widget.*`, and inlines `src/<id>-lib.js`, then any `src/<id>-lib-*.js` in name order, wherever a script has `/*__LIB__*/` (and any `src/<id>-lib-*.css` ahead of the page's own CSS, for a library that brings a stylesheet). A shared library with no page in it can be run on its own by a check (`tools/check-travel.mjs` does this for the Travel module's model and plan).

### Shared tools

The SDK carries what more than one module needs (the date picker, the action menu, the editor window `host.ui.editor` -- a module's Add or Edit form as a modal dialog over the whole page, sized to the form and a sheet in the narrow layout, with the close button, Escape, the "Discard your changes?" question and focus on close written once; in a sandboxed frame the host lifts the frame itself to the same size ("The frame" below) -- the kind picker `host.ui.kindPicker` -- one field for choosing the kind of a thing from named, iconed, coloured options in groups, typing to filter, the recent choices first; the Planner's **What is it**, written once for Research's note type and Places' category to take later -- the drop decision `host.objects.dropMenu` -- what dropping one module's object on another can do, one menu for every module, filled from what the modules around declare -- and small helpers in `host.util`), so modules stay small and look and behave alike. The picker and menu draw their elements inside the module's own root, positioned by the page's coordinates, and add their styles once to that root in the theme's colours, so they work in a frame and in the page; opened from inside an open editor window they draw inside that dialog instead, so they share its top layer ([architecture-module-window](architecture-module-window.md), "The editor window"). The rule for the SDK: when a second module needs something a first one wrote for itself, it moves into the SDK and the first module uses it from there.

### Settings

`server/module-settings.js` keeps what people chose for the settings a module declares, in `DATA_DIR/modules/settings.json`: `{ environment, spaces, people }` (it was `{ server, rooms, people }`), one bucket for the environment, one per space and one per person, each holding a module's values. The manifest's definitions are cleaned in `cleanSettings` (`server/modules.js`) and every value is checked against its definition on the way in. `GET /api/modules/:id/settings/values` gives a module the values that apply to the viewer (the environment's, the space's and the person's, defaults filled in), and a change goes out on the shared stream as `settings` so open modules read them again. Who may change what is decided in `settingsPlace` in `server/index.js`: an owner for the environment's, an owner or a member ticked as a moderator in that space for the space's, and anyone for their own. The forms are drawn by `public/module-settings.js` (the Modules tab for the environment's, the **Modules** tab of the space's Set up panel for an owner or a space's moderators, in its draft mode so Set up's Save sends them, and the profile page for a person's own). The old `/module-settings?space=<id>` address redirects to that tab. Changes to environment and space settings add a line to the activity list; a person's own do not.

### Run modes

`runModeOf` in `server/modules.js` decides how a module runs: the admin's explicit choice, else the page for a module installed from those that ship with Chameleon (`source: 'bundled'`), else a sandboxed frame. Switching an uploaded module to the page needs `acceptRisk`, and the server records when. The frame path is described below. For the page, `/m/<id>/<version>/<entry>?part=css|body|js` returns the style, the markup and the script of the module's single HTML file, and answers 403 unless the module runs in the page. `startInPage` in `public/module-host.js` attaches a shadow root to the module's container, injects the base stylesheet (scoped) and the module's style and markup, and loads its script as an external script carrying the SDK instance (the space page's content security policy forbids inline script). The SDK is the same code (`createHost`); over a frame it talks by `postMessage`, in the page the host calls its handlers directly. A module in the page can bypass the SDK, so the approved-permissions list, which the server checks per call, stops being a limit on it; that is why the choice is the admin's, behind a warning. The Maps module shows how a large front-end library rides in a bundled module: MapLibre GL JS and the PMTiles reader are `src/maps-lib-*` files inlined into its page, the map's worker starts from a blob (the page policy allows `worker-src blob:`), the map file is read by range from `GET /api/modules/:id/files/:name` (the operator's file in `DATA_DIR/modules/<id>/<folder>/`, the folder its `file` setting names; installing, updating and uninstalling never delete it, even when the module's data is wiped, chosen by a `file` setting), and the label glyphs are static files under `public/maps-glyphs/`. `GET /api/modules/activity` (admin) lists what modules have done recently, shown on the Modules tab; the list (300 lines) is written to `DATA_DIR/modules/activity.json` a few seconds after a change and when the server stops. `server/module-limits.js` rate limits what goes through the API per module and person (saves, events, actions, schedules, notifications, searches, uploads, AI requests and object checks) with a sliding minute; it limits only what passes through Chameleon, so it is not a boundary for a module running in the page.

### Picture maps

A picture map lets an owner use an invented world, drawn from a picture, as the whole environment's map ([plan-map-image](../plans/plan-map-image.md), Thomas's decision 3: the owner makes a raster PMTiles file and uploads it). The flow, end to end:

1. **Declared.** A module's manifest has a top-level `pictureMap: { setting }` naming a `file` setting that declares `upload: { accept: 'pmtiles-picture' }` (`cleanPictureMap()` and the `file` setting's `upload` check in `server/modules.js`; Maps' `imageMap` is the one). An installed manifest whose `pictureMap` no longer passes is read with none.
2. **Uploaded.** The owner picks a `.pmtiles` file in the setting's form. The page sends it with `PUT /api/modules/:id/files/:folder?name=` (`application/octet-stream`). The route (`server/index.js`) streams the body to a part file in the setting's folder with a running byte count, so a large file is never held in memory, stops at the limit (`MAP_IMAGE_MAX_MB`, default 100), reads the 127-byte PMTiles header (`pmtilesInfo()` in `server/pmtiles-header.js`) and refuses a file whose type is not picture tiles (map data, an unknown type, a zoom range above 22, or a cut-short file), and only then renames it into place, points the setting at it and removes the file it replaces. One upload runs per module and folder at a time. A failure at any step leaves the old file and setting exactly as they were. Every status and sentence is in [api-modules](../api/api-modules.md), "Picture maps".
3. **Seen.** `pictureMapOf()` reads the setting and the file's header on demand, so there is no copy to go stale: the picture map is `{ file, minZoom, maxZoom, tileType }` while the setting names a file that is there and whose header says picture tiles, else none. It is on `GET /api/modules/:id/context` as `environment.pictureMap`, so every module's hello carries it (`host.environment`), and `module-host.js` tells open mounts when it changes (the `environment` event). `GET /api/modules/:id/geocode` answers "configured: false, pictureMap: true" for every module, so no outside place search runs and no real-world place is read or saved.
4. **Kept apart from map data.** The module's `files` setting for ordinary map data refuses a picture file newly ticked in it, and the picture setting refuses a file that is not picture tiles (400, in `PUT /api/modules/:id/settings/environment`), so each file is drawn the way it was made.
5. **Drawn.** Maps reads the file by range from `GET /api/modules/maps/files/<name>?folder=image-map` (the `folder` keeps the picture's name from clashing with a map data file of the same name; a `Range` that cannot be met answers 416 with the file's size) and draws it as the only layer: `buildPictureStyle()` makes a style with the theme's background and one `raster` source `pmtiles://<address>` with 256-pixel tiles and the file's own zooms and bounds, and `pictureLimits()` holds panning to the file's bounds.

**The placement rule.** MapLibre draws only the web map's projection, and PMTiles holds tiles by zoom, column and row in it. A picture has no coordinates, so one rule places every picture: its **longer side spans the whole web map square**, centred on 0,0. A picture `W` by `H` pixels, with `S` the longer, covers `-E*W/S` to `E*W/S` across and `-E*H/S` to `E*H/S` down, `E` being 20037508.34 metres, half the square. Zoom 0 is the whole picture in one 256-pixel tile and each zoom doubles it, so the most detailed zoom a file needs is `ceil(log2(S / 256))` (6 for 16384 pixels, 5 for 8192, 4 for 4096). The file's own header states the zoom range it was made with, and **the map never zooms past the file's own maximum** (it would only blur): the map's `maxZoom` is the file's, a selected place, a new pin and a fit land one level shallower than the file's deepest zoom (never shallower than its minimum), and every fixed zoom (a pin, a pasted position, a cluster, a remembered view) goes through `capZoom()`. Positions stay `{ lat, lng }`: a pixel and its fake position convert both ways with the web mercator formulas, so places, summaries, pointers and every other module's objects keep working unchanged. The picture is drawn undistorted; only the derived latitude bunches up towards the top and bottom, which nobody sees as long as nothing measures with latitude and longitude. Places saved before the switch keep their positions and are neither hidden nor moved. `tools/check-picture-map.mjs` holds the route and `tools/check-picture-map-page.mjs` the page side.

### The frame

A module page is served from `/m/<id>/<version>/<file>` by `server/index.js`. Only the active version of an enabled module is served, and the path is checked to stay inside the version folder. The response carries `Content-Security-Policy: sandbox allow-scripts allow-forms; default-src 'none'; script-src 'self' 'unsafe-inline'; ...; connect-src 'none'; form-action 'none'`, so even when opened directly it has an opaque origin, no cookies, and no network beyond loading its own files. The host also sets `sandbox="allow-scripts allow-forms"` on the iframe. `allow-forms` is there because a sandboxed frame without it swallows a form's `submit` event, so a module's Save button appears to do nothing; `form-action 'none'` means nothing can actually be submitted.

HTML pages are rewritten on the way out: the SDK and the base stylesheet are injected inline right after `<head>`, unless the page already includes `/sdk/host.js` (the SDK) or carries `<meta name="sdk-base" content="none">` (the base styles). Inline injection means a module needs no subresources at all, so it works wherever a sandboxed frame may not load its own files.

A frame has one way to draw something bigger than its box: the **lift** for an editor window ([plan-editor-window](../plans/plan-editor-window.md), step 11). A modal `<dialog>` inside a frame is in the frame's own top layer, not the page's, so when a module in a frame opens `host.ui.editor` the SDK asks the host over the bridge (`editor.lift`, `{ open, size }`) and `mountModule()` in `public/module-host.js` lifts the frame itself: the class `module-editor-lifted` (and `module-editor-lifted-large` for `size: 'large'`) makes it `position: fixed`, centered, exactly the editor's size (560 or 880 px wide by the viewport's height less 48 px; a full-screen sheet at 640 px and below), a `div.module-editor-backdrop` goes in before it, and everything else on the page is made `inert` the way a modal dialog does it (every sibling of the frame and of each of its ancestors up to `<body>`: the header, the other modules, the floating layer, the module's own bar and toolbar). The host answers `true`, and the SDK gives the dialog `sdk-editor-lifted` so it fills the frame; the frame is the window. The lift is put back when the module's last open editor closes, when the frame loads another document (`load`), when the mount is destroyed, and by `public/canvas.js` before it moves the module between docked and floating (the SDK asks again on `moved`); a floating module's box is brought to the front while lifted. A module in the page gets `false` (its dialog is already in the page's top layer), and so does a module in a window of its own (`lift: false` from `public/module.js`; the frame fills the window). The styles are in `public/style.css` between `lift:start` and `lift:end` (at the menus' level, `--z-menu`: above the floating layer, under the pages opened over the call) and in `/sdk/host.css`. How it fits with the editor window is in [architecture-module-window](architecture-module-window.md), "The editor window"; `tools/check-module-host.mjs` runs the lift on a stand-in page and `tools/check-module-window.mjs` holds the SDK and the stylesheets to it.

### The bridge

`public/sdk/host.js` (in the frame) and `public/module-host.js` (in the hosting page) speak a small `postMessage` protocol: the frame sends `{ host: 1, id, method, params }`, the host answers `{ host: 1, id, result | error }`, and pushes `{ host: 1, event, data }`. The host answers only messages whose `source` is its own frame's window (the frame's origin is opaque, so the origin cannot be checked). In the other direction each frame gets a random secret in its address (`?tk=`), every message the host sends carries it, and the SDK ignores messages without it; who sent a message cannot be the check, because when the call is popped out the host code runs in a different window from the frame's parent. Each method becomes an authenticated HTTP request on the frame's behalf; the frame never holds a session.

A module's add actions ride the same bridge: `add.set` gives the host a list of entries (leaves, one level of categories and dividers), the host draws them as the **+** in the module frame's title bar (`cleanAddEntries()`, `addPlan()` and `frameAdd()` in `public/module-chrome.js`; a single leaf runs at once, more open the shared menu with a category's leaves in a flyout) and sends each pick back as an `add` event. `status.set` gives it up to four items for the status bar at the foot of the module's window, read out politely only once the items have been still for 1.5 seconds. The host validates both (labels up to 40 characters, status text up to 60, icon names limited to Font Awesome names, tints limited to the eight, at most 8 top-level entries, 12 leaves in a category and 40 in all, and at most 4 status items; `tools/check-module-chrome.mjs` runs the rules); the calls answer `true` wherever a module is drawn in the frame, and `false` only for a dashboard widget, where the module keeps its own. The old `bar.set` is kept: `foldBarItems()` turns its buttons into leaves of the same **+**, and a pick still arrives as the `bar` event. `attention.set` and `attention.clear` are sent to the attention routes for the module in its space (only for a signed-in person in a space; anywhere else they answer `false`), and tell the page, which reads the sum again. The shapes are in [api-module-sdk](../api/api-module-sdk.md); the module frame is in [architecture-module-window](architecture-module-window.md).

Two more things the bridge carries. An action request asked with `here: true` has the host add the asking page's id and a time limit five seconds on (`pageInput()` in `public/module-host.js`), and a providing mount takes only requests meant for its own page (`forThisPage()`): that is how two modules in one page talk without a stray tab answering. And the hello carries the environment's facts (`environmentFacts()`, from `GET /api/modules/:id/context`): the picture map, or none. A mount reads the context again a moment after an environment setting changes and sends the `environment` event when the facts differ (`recheckFacts()`).

The host passes the theme in `hello` as a set of CSS custom properties read from the page's computed style, and the SDK sets them on the frame's `:root`.

### Who may do what

Every runtime route calls `moduleAccess` in `server/index.js`, which resolves the module (it must be enabled), the caller (a signed-in user, or a guest with a space's guest link token), the scope, and for a space scope checks that the module is on for that space and the caller is in it. That holds for a module's environment page writing into one of the caller's spaces (`scope=space&space=<id>`, the SDK's `{ space }`): `scopeOf()` in `public/module-host.js` (the pure `placeOf()`) only shapes the request, letting an environment mount name a space and keeping a space mount to its own, and the server applies the same check as for a page in that space. `GET /api/modules/:id/spaces-data` gives each space `write`, the module's `write` permission there, so an environment page offers adding only where it may (the Calendar's, To-do's and Places' **Where**). It then checks the module's `access` permission through `store.spacePermissions`, so the Moderator grant for a space applies to modules too. The module's permissions are added to the Roles grid at run time: `ModuleManager.permissionList()` supplies `module.<id>.<key>` entries, `store.extraPermissions` hands them to `Store.roleSet`, and `store.allPermissions()` feeds the Roles grid.

### Data

`server/module-data.js` keeps a key-value store per module and scope: `data/modules/<id>/data/environment.json` and `space-<id>.json` (named `server.json` and `room-<id>.json` before the Names migration's `names-spaces` part, which moves them; uploads likewise sit under `uploads/environment/` and `uploads/space-<id>/`). Inside the host a scope is a key: `environment`, `space:<id>` or `person:<key>`. Each scope loads once into memory and is rewritten whole on a change. Every key carries a version; a write that names a stale version gets a conflict carrying the current value. The 5 MB cap is checked against the module's total data on disk. Each write emits a `change` event.

### Personal data

A module that declares the `person` scope keeps data per person (`DATA_DIR/modules/<id>/data/person-<user key>.json`, with the same versions and 5 MB cap as a space's). The route never takes a person from the request: `moduleAccess` names the store from who is signed in (`person:<key>`), so one person cannot ask for another's, and an administrator is a person like any other here. Change events for it are sent only on that person's own streams (`place()` in the modules stream checks the key). Pointers carry `scope: 'person'` and resolve against the viewer's own store, so a pointer someone else holds shows as gone; links (`setLinks`) refuse personal objects on both sides, so the shared link store never learns of them. Guests have no personal data. A person's data (`data/person-<key>.json`, its hold in `trash/` and `uploads/person-<key>/`) is private to that person, even from admins: an owner's export leaves it out (see [architecture-environments](architecture-environments.md), "The owner's copy and a restore"). The host's full backup is complete and does carry it.

### Live changes

`GET /api/modules/stream` is one server-sent event stream for every module on a page. It subscribes to `change` events from the data store and `fire` events from the scheduler and writes them as `change` and `schedule` events, each labelled with its module and a scope (`space`, `environment` and `person` for a space's modules, `environment`, `person` and `spaces` for a module's environment page) and a `spaceId`, checked against what the viewer may read. `public/module-host.js` shares one stream per space and page between all its frames and forwards each event into the right one. This matters because browsers allow only about six long-lived connections to one host over HTTP/1.1: a stream per module (two for a module on the canvas) used them all with three modules open, and every other request, including a frame's first call to the host, waited forever, which the frame reported as the host not answering. `GET /api/modules/:id/events` remains for a single module and scope.

**Window frames share the page's stream.** A destination's page in a window frame on the Workspace (the Map's `/map?space=<id>`, the Calendar's) would be a second reader of the same stream, and a browser's six connections to one site ran out. So `public/module-stream.js` gives the page one hub (`createStreamHub`) that opens as few connections as the views wanted need: the page's own view and one space's ride one connection (`?space=<id>&page=1`), any other space has its own. When the views change, the new connection opens first and the old one closes only once the new one is open; an event both carry has the same `id:` and is handed on once. A frame does not open a stream. It asks the page over `postMessage` (`createStreamRelay` on the page, `createStreamRelayClient` in the frame): `app:streamjoin` and `app:streamleave` go up with a `doc` token of the frame's document and a `sub`; each event comes back as `app:streamevent`; a relay made again for the same frame says `app:streamhello` and the frame joins again. The page grants only the view the frame was made for (its space and its guest token), both sides check the other's window and origin, and each mount's own filtering still decides what each module hears. A join the page does not answer is asked again at 1, 2 and 3 seconds, and after about ten seconds the frame opens a stream of its own, so it is never left without live updates. When the call is popped out into a window, the frame loads there and hears the page that opened it (`opener`, only while it is this site's). `tools/check-streams.mjs` runs the hub and the relay against a stand-in event source and clock.

### Objects

**The principle.** Chameleon is the conduit and the transport; it does not know what a task, an event or a poll is, and no code in it, or in one module, is written for a particular other module. Everything that lets modules work together is declared by the modules (what they share, what they can open, what they show links to, what they want to link to) and carried out by generic routes that read those declarations. If a change to Chameleon names a module, or a module lists other modules by name in its code, the design has slipped. A module installed tomorrow takes part by declaring, and the modules around it need no change: linking a to-do to objects of a module written after it works because the To-do consumes `"*"` and asks Chameleon what it may link to.

Modules cannot read each other's data, and pointers to objects are the single, declared exception. The stored `module.json` is the author's original, so `cleanRefs` in `server/modules.js` normalises `refs` when a manifest is installed and again whenever one is read (`manifestOf`). A producing module maps a kind to a stored key (`event:{id}`) and to summary fields (`refs.produces[].summary`; `card` before step 7 of the Names plan, now refused); a consuming module lists `module:kind` entries an admin must approve. Because modules are front-end only there is no provider code to ask, so the summary is built by the server from the provider's stored value, and only the named fields are copied.

The routes in `server/index.js` (`/api/objects/resolve`, `/api/objects/search`, and one summary by address; `/api/refs/*` before step 7, now 404) all pass through `refScope`, which checks, in order: the asking module is named, the provider is enabled and produces that kind, the asker declared and was approved for `provider:kind`, the scope exists (a space the viewer may open, or the environment for a signed-in person), and the viewer holds the provider's `read` permission there. Missing or refused objects come back as an error per pointer, never a stack trace or a partial record. `GET /api/objects/search` reads one scope, or with `scope=spaces` each space the viewer is a member of in turn through `refScope` (so each provider only where it is on and readable), each pointer carrying its space; `has=place` keeps the summaries with a place and raises the cap from 50 to 1,000, for a map that needs every pin. The host (`public/module-host.js`) always sends the frame's own module id as `from`; that is a consistency check rather than a security boundary, since the viewer is the one authorised, and their own permissions in the provider are what decide the answer.

A consumer stores only `{ module, kind, id, scope, space? }` (`scope` is `environment`, `space` or `person`) and resolves it each time it draws. Two more conduits build on the same pointers. **Opening**: `objects.open` asks the page to show an object in the module that owns it (`openRef` in `public/canvas.js` opens it on a space's canvas; `public/module.js` goes to its page), and delivers an `objectopen` event, which the owner's `host.objects.onOpen` turns into showing the object; nothing is known about the object. **Links**: a module tells Chameleon what its own objects point at (`POST /api/objects/links`), which `server/module-links.js` keeps as pairs of pointers, never content; the module that owns an object marked `backlinks` can then ask what points at it, and every answer is resolved through the source module's own read permission for that viewer, so a link is only as visible as its source. A change is announced to the affected modules as a `links` event on the shared stream. Dragging is brokered by the host and driven by the pointer, because the browser's drag and drop does not reliably deliver a drag from one sandboxed frame into another. The source frame's SDK (`host.objects.draggable`) follows the pointer (captured from the press, so it is followed outside the frame too) and tells the host where it is in the frame's own coordinates (`objects.ptrStart`, `ptrMove`, `ptrDrop`); `ptrBegin`, `ptrMove` and `ptrDrop` in `public/module-host.js` convert to the page's, find the module frame under the pointer, draw the label at the pointer, and forward `over`, `leave` and `drop` to that frame in its coordinates (the `objectdrag` events that `host.objects.dropTarget` turns into callbacks). It only works between frames in one window. An earlier design put transparent layers over the other frames for a native drag; that path (`objects.dragStart`) is still there for a native drag, and the older text follows.

Native drag, for reference:  `host.objects.drag` sets the pointer on the drag (`application/x-host-object`, carrying `{ ref, summary }`, for a drop into a frame in another window) and tells the host (`objects.dragStart`, checked for shape). `beginDrag` in `public/module-host.js` then puts a transparent layer over every other module frame on the page; the layers are in the host's own page, so they receive the native drag, and forward `over`, `leave` and `drop` to the frame beneath in that frame's coordinates (`objectdrag` events, which the SDK's `objects.dropTarget` turns into callbacks). The layers come down on the source's `dragend`, on a drop, on a click, or after 20 seconds, so a module cannot leave them up. A receiver validates the pointer's shape and resolves it, so a forged drag reveals nothing.

### Data guards

`access.read` and `access.write` say who may use a module's data at all. Some rules are finer and belong to the module: only the voter writes a vote, only the person who added a photo or a manager changes it, a closed poll takes no more votes, a cost is not for guests. A module declares those under `guards` in `module.json`, and `server/module-guards.js` holds the data routes to them (`checkPut`, `checkDelete`, `checkClear`, called from `PUT` and `DELETE /api/modules/:id/data`). The module's own page may check the same things for a friendlier screen, but the server no longer relies on it: a module in the page can bypass the SDK, and a frame can be edited.

The file knows no module. It reads a manifest's `guards` once, at install (`cleanGuards`), and again on every read of a stored manifest; a manifest whose guards no longer read is kept as `{ invalid: true }`, which refuses every write, rather than dropping the guards, and fails closed for guests (`shut`). A rule answers with the value to store, perhaps with the server's own fields set (the writer's name, who added it), or one sentence and a status. The same file removes the `hidden` fields from what a guest receives, and `server/index.js` calls it wherever a stored value leaves: the data routes, the live stream, summaries, search and the published calendar. A space's `guestsSeeHidden` opens them for that space. `access.personWrite` lets a module name a different permission for writing a person's own data. The contract, with every field and refusal, is in [api-modules](../api/api-modules.md), "Data guards". `tools/check-module-guards.mjs` runs the rules and the routes against throwaway servers, with a module made for the purpose and with Research.

### Clear and Undo

A module's **Clear** (the last entry of the titlebar menu, in red) removes everything the module holds in one place, and the person has a short time to take it back. The server holds what was cleared and decides when the hold is over. The Undo itself needs the `restoreToken`, which only the page that cleared has, in memory: close or reload that page and the Undo is gone, though the data stays held until the time runs out. (The dialog says so: "You can undo it for 30 seconds, until you leave this page.")

- **The hold.** `DELETE /api/modules/:id/data` moves the module's values for that scope into a hold (`server/module-holds.js`, `DATA_DIR/modules/<id>/trash/<scope>.json`: `environment.json`, `space-<id>.json` or `person-<key>.json`), empties the scope in one write and answers a `restoreToken`. The hold lasts `CLEAR_UNDO_SECONDS` (a whole number from 1 to 600; 30 if unset or not one) and five seconds' grace for a slow network. There is one hold for a module and scope, so a second Clear there is refused (409) while one is held. The sentence counts to `undoUntil`, the time the page shows; in the five seconds of grace after it, it says when a clear is possible again.
- **What waits.** The uploaded files the values name stay on disk, and what the clear would do to other modules (their dated copies, their pointers) is not done, until the hold runs out, when `finishHold` does it. A file a hold names cannot be removed in the meantime (409).
- **Undo.** `POST /api/modules/:id/data/restore` with the `restoreToken` puts back exactly what was held, each value with its writer and time, in one write and one `changes` event. It counts as one save against the write limit and needs the same permission as the Clear. A key that holds something by then keeps it and is named in `taken`; the rest come back, and what did not is finished like an expired hold. A token that undoes nothing is 410, and says whether the clear was already undone, was replaced by a later one, or the time is over.
- **Restarts.** Holds are on disk. On start the server arms a timer for each, and finishes those whose time ran out while it was down. A hold file it cannot read is logged and set aside as `<name>.bad`, so nothing waits on it for ever. Turning a module off finishes its holds first, and so does an update, install or rollback that turns it off to ask for approval (`modules.beforeOff`, which also finishes the holds of the modules that need it), a set-aside environment stops its hold timers, and a file setting cannot name `trash`, `data`, `uploads`, `library` or `versions` as its folder.
- **Limits.** A module is cleared at most five times a minute in an environment, by everyone together (429, `Retry-After`). Two more counts keep that fair (`clearBudget` in `server/index.js`, `clearPerson` and `clearOrdinary` in `server/module-limits.js`): one person may take 3 of the 5, and everyone who is not an owner, the admin or a moderator of the space takes 3 between them, so the last two are always there for a moderator. A refused clear gives back what it had counted. A hold is never bigger than the module's own data cap (5 MB).
- **Bookkeeping keys.** A key that starts with `_` is the module's housekeeping, not an object. It goes and comes back with the rest but is not counted or named.
- **The event.** A Clear and an Undo each send one `changes` event for all their keys, marked `cleared: true` or `restored: true`. A batch bigger than 256 KB goes without its values and with `reload: true` (`emitBatch` in `server/module-data.js`). Written out once for all open streams, and a viewer's permissions are worked out once per person for the turn, so a big Clear costs the same with ten streams open as with one. The host passes the event to the frame as `changes`; the SDK gives a module with no `changes` listener one `change` for each entry (reading the values first if they are missing), and a module with a listener reads the data again when an entry has no value ([api-module-sdk](../api/api-module-sdk.md), "Live changes").
- **Who may.** The module's `write` permission, and the guards' `clear` rule when it has one (`checkClear`). A writer who cannot see a module's hidden fields cannot clear what holds any. `GET /api/modules/for-space` says it for the canvas, as `clear`, and carries `undoSeconds`; the canvas offers **Clear** only where `clear` is true, which is also never for a library module (the Vault holds files, not data) and not while the module holds no objects in the space or an earlier Clear there can still be undone.
- **The page.** `openClearMenu` and `clearWithUndo` in `public/module-host.js` ask the person to type the module's name and run the Clear inside the dialog, so a refusal (the 409 and 429 sentences) is read where it was asked and the dialog stays; then it shows "Cleared <name>." with **Undo** until the time is over by its own clock. A failed Undo (storage full, no network) shows the server's sentence and may be pressed again until then. `followClearable` asks `GET /api/modules/for-space` again after a change that could flip `clear`, and once more when the hold and its grace are over. The contract is in [api-modules](../api/api-modules.md), "Runtime routes".

The Planner declares a `clear` permission, **Clear the whole trip**, that its guards name; it starts on for moderators and off for members, and an owner may grant it on the **Roles** tab.

### Library modules: the Vault

A module that declares `"library": true` keeps a space's files, and the host serves them (the Vault is the only one so far; the plan is [plan-attachments-vault](../plans/plan-attachments-vault.md)). The core names no module: the routes are under `/api/modules/:id/library` and work for any module whose manifest says `library`. The manifest needs the `space` scope and the permissions `view`, `add`, `download` and `remove_any` (`cleanLibrary` in `server/modules.js`); a library's permissions are never on for guests, in the manifest's defaults or on the Roles tab, and every route refuses a guest and the access key.

- **Files and records.** A file's bytes are `<bytes folder>/space-<space id>/<file id>.bin`, and its small picture `<file id>.thumb`. The bytes folder is `VAULT_DIR/<environment slug>` (`_default` on a single-environment install), which is outside the in-app backups. The records (`id`, `name`, `type`, `group`, `size`, `sha256`, `by`, `at`, `taken`, `camera`, `thumb` and `viewable: false` for a download-only PDF) are in `DATA_DIR/modules/<id>/library/space-<space id>.json`, so a backup carries them; `server/vault-store.js` writes each through a temporary file and a rename, and a sweep on start tidies what is left (below). Nothing a person sends names a path. Deleting a space deletes its files and its share links (`forgetSpace`, called from `server/space-erase.js`), and uninstalling a module with its data deletes the bytes, the records and the links.
- **What a file is** is decided from its own first bytes (`server/vault-types.js`), then compared with its name and the type it was sent with; a mismatch is refused, and so is anything not in the table (SVG, HTML, scripts, programs, archives, Office files, Matroska and HEIC). The limits are 25 MB for a picture, 200 MB for audio, 2 GB for video, 100 MB for a PDF and 1 MB for Markdown, and a picture of more than 100 million pixels is refused.
- **Quotas.** A space, a person (across an environment's spaces), the environment (a hosted plan's storage cap) and the server each have a total; an upload reserves its `Content-Length` against all of them before a byte is read. The owner's two settings on the module (`spaceMaxGb`, `personMaxGb`) can only lower the variables below. Other people's uploads still arriving count against yours for at most half of what is free, and a file is checked against the disk again once it is in; a hosted server may pass its total briefly (Thomas, 2026-10-31).
- **Uploads.** The body streams to a part file as it arrives and is never held in memory. It is looked at (the head), hashed on the way, and cut off if it arrives slower than the floor. At most two uploads at once for one person and eight for one environment, 12 open file streams for a person and 100 for an environment, and 500 MB a minute for a person. Requests are counted apart from a module's picture uploads (`library`, `libraryThumb` and `libraryAll` in `server/module-limits.js`): a file and its small picture are two requests, so a drop of 200 files is 400. A person may make 400 file requests and 400 small-picture requests a minute, and the environment 1,500 of the two together; a request counts for both, and is given back for the person when the environment's count refuses it. Over either is 429 with `Retry-After` and "<module's shown name> is busy. Wait N seconds and it will carry on." Reading a file or its small picture is never counted. Every module's 429 from the per-module limits uses that sentence (`limitMessage` in `server/index.js`); the module's page waits the `Retry-After` it is given (up to 2 minutes).
- **The scan.** After the upload, the whole file is checked in a worker thread (`server/vault-scan.js`), never on the main thread, within `VAULT_SCAN_SECONDS` and a memory limit. A picture is read and cleaned: what rides along in it is taken out, the time it was taken and the camera are kept in its record, and where it was taken stays only when the upload asked for it (`keepPosition=1`). An MP3, MP4, WebM, WAV, Ogg or Markdown file's structure is looked at.
- **PDFs** (`server/pdf-scan.js`) are read as syntax, token by token, in 1 MB windows, within a budget of objects, streams and decoded bytes. A PDF is refused when it holds any of these names, anywhere, including in an object stream: `JavaScript`, `JS`, `AA`, `XFA`, `ResetForm` (scripts), `Launch`, `GoToR`, `GoToE`, `ImportData` (opens programs or files), `SubmitForm` (sends what is typed), `EmbeddedFile`, `EmbeddedFiles`, `RichMedia`, `EF`, `AF`, `Collection`, `Rendition`, `Movie`, `Sound` and `3D` (files of its own); or a link (`/URI`) to anything but a web page or an email address. A damaged PDF is refused too. Links to web pages, going to a page, named actions and fillable forms that do not send or run anything are allowed. A PDF the scan could not judge (encrypted, an object stream it cannot decode, or past its budget or time) is kept as download only: its record has `viewable: false`, and it is sent only as a download.
- **Serving.** A file is sent with `Content-Type` as stored (Markdown as plain text), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cache-Control: private, no-store` and `Cross-Origin-Resource-Policy: same-origin`, with range requests. A PDF is always an attachment, never opened in the browser at this site's origin.
- **The PDF viewer.** The app's own viewer is `GET /viewer/pdf`, an HTML document (`server/pdf-viewer.js`) sent with a content security policy that allows no network (`connect-src 'none'`), no frames, workers, forms or plugins, and only this site's scripts and styles, and with `sandbox allow-scripts`, so it runs as a null origin. The page that shows a PDF frames it in `<iframe sandbox="allow-scripts">`, fetches the PDF with the person's session (`host.library.blob`) and hands it to the frame by `postMessage`; pdf.js parses it on the frame's own thread. pdf.js is vendored in `public/sdk/pdfjs/` (pdfjs-dist 6.4.299, the legacy build), served at `/sdk/pdfjs/*` with `Access-Control-Allow-Origin: *`, and each file's SHA-256 is pinned in `tools/check-vault.mjs`, which fails on a changed, missing or unpinned file. The frame's own script is `public/sdk/pdf-viewer.mjs`, whose top comment is the protocol.
- **Request bodies.** Every other route's body must arrive within `REQUEST_BODY_SECONDS` (300) of its headers or the connection is closed. Only a library upload and a library small picture are exempt, since a 2 GB file on a slow link can take far longer; each cuts off one that is too slow by itself. The server's own request timeout is two hours.
- **The windows.** A file opens in `public/file-viewer.js` (views in `public/file-viewer-views.js`): the module frame's window variant, in a layer over the canvas, up to four at once, with **Close all** in the Layout menu (`public/canvas.js`). A module opens one with `host.files.open`.
- **The sweep on start.** Once, when an environment's store is made and before anything arrives, `sweep()` in `server/vault-store.js` removes unfinished uploads (part and temp files), bytes no record names once they are a week old, space folders left empty or belonging to a space that no longer exists, and the records and share links of a deleted space. A record whose bytes are gone is kept and counted, not removed (below). It stops after `VAULT_SWEEP_SECONDS` (10) and finishes on the next start; it never touches a module's data, a Clear's held data or a file whose space exists and whose record names it. When it finds anything the log has one line, "Library sweep of <folder>: ...", with the counts.
- **Missing files.** A record whose bytes are not on the disk (a data backup restored without `VAULT_DIR`, a lost disk) is shown, not hidden: the list carries `missing: true`, the bytes route answers 404 with `missing: true`, an object summary carries `missing`, and a chip reads "File missing". The person removes the record. `docker-compose.yml` keeps the bytes in a volume of their own (`/app/vault`, set by `VAULT_DIR` in the image), which the in-app backups do not carry; back it up with the data folder.
- **Linking from other modules.** A file is an object of kind `file`, with its record in `DATA_DIR/modules/<id>/library/` rather than in the module's data, so `objectRows` and `objectValue` in `server/index.js` read the records for that kind wherever objects are listed, searched or resolved. A module attaches files with `POST /api/objects/links` carrying `kind: "file"` and `op: "add"` or `"remove"` (`ModuleLinks.set` in `server/module-links.js` changes only the links of that kind and leaves the others, which count against the 20 an object may hold). A link to a file that was removed is kept when the object already held it: it reads "File removed", and its holder can take it out with **Remove link**. Removing a file tells the holders (`links` event), so their chips change at once. A guest never sees a library's files. The SDK pieces are `host.files` and `host.ui.fileChips` ([api-module-sdk](../api/api-module-sdk.md)); `host.objects.open` on a file pointer opens the file window and refuses a file of another space with "That file is in another <space>. Open it there."
- **The library event.** `VaultStore` is an event emitter: adding, renaming, removing and giving a small picture each emit `change` with `{ module, spaceId, op, id }`, and the modules stream turns it into a `library` event for each viewer who may read that library in that space (never a guest), naming the modules that should look again: the library and the modules approved to link to its files. Only ids go. The Vault's page keeps its 15 second check as a fallback, and a file window follows the event, so a rename shows in its title and a removal turns it into "File removed".
- **Share links.** `server/vault-share.js` holds the routes and `VaultStore` the records (`DATA_DIR/modules/<id>/library/space-<space id>.shares.json`). The maker needs the module's `share` permission (off for members, on for moderators); changing a link's name or files is for its maker or an owner, and turning it off for its maker, an owner or a moderator of the space. A link is a set of 1 to 500 files with a name, an end of 1, 7 or 30 days, a choice of download and an optional password of 8 characters or more. The token is 32 random bytes, shown once and kept as a SHA-256 hash; the password is kept as a scrypt hash. At most 200 links are held for a space, and ended ones go from the list and do not count. A link is its maker's: on every open the server asks whether they still exist, are in the space (or are an owner or the admin) and still hold `share`, and `download` if the link allows it; if not, the link answers as ended. It also ends when it is turned off, when its last file is removed, when the module is turned off for the environment or uninstalled (the records go, so a module turned on again gets its files back and no old link), and when the space is erased. Turned off in one space only, the links there stop answering and return when it is turned on. `GET /shared/<token>` serves one page for every token, with a content security policy that allows only this site's files and the PDF viewer frame, no framing, no referrer and no indexing; the page asks `/api/shared/<token>`, which answers 404 "This link has ended." for any link that does not open, whatever the reason, so a stranger learns nothing about a link. The password unlock sets a cookie that goes only with that link's own routes (`Path=/api/shared/<token>`), is signed over the link, its token hash, its password hash and its end, and lasts an hour or to the link's end. The limits against guessing are in [api-modules](../api/api-modules.md), "Share links", and an address is `req.ip`, so `TRUST_PROXY_HOPS` must match the number of reverse proxies (0 when the container is reached directly). A hosted server answers a link only on its environment's own host. The share sheet and the list of links (`public/share-sheet.js`) are drawn in the page by `host.library.share` and `shares` and by a file window's **Share** button; the public page is `public/shared.html`, `public/shared.js` and `public/shared.css`, using the file windows' views.
- **Who can see a file.** ([plan-vault-privacy](../plans/plan-vault-privacy.md), slice 1, held; no screen yet.) A record may carry `visibility` (`only-me` or `people`, with `people`, a list of user keys of at most 200); a record without it is seen by everyone in the space, and the field is written only when it is not. The rule is written once, in `fileVisible` in `server/index.js`. A viewer sees a file when they added it, are an owner or the admin, hold the module's `see_all` permission ("See every file", off for every role by default, never on for guests), the file is for everyone, or it is for chosen people and they are listed and still a member (a listed key that is not a member now grants nothing, and stays in the record). Who may change it is `fileManageable`: the adder, an owner or the admin. Every route about one file finds its record through one door, `libraryFile`, so a file the viewer cannot see answers as a missing one (404, the same text and headers), whatever the route. The reason is that a difference between "not there" and "not for you" would tell a person that a file exists. `tools/check-vault-visibility.mjs` fails on a route that reads a record another way.
  - **Objects.** The object chokepoint (`resolveRef`, `objectRows`, `objectValue`) applies the same rule after the module check. A hidden file is a 403 `unseen`, never a 404, so a link to it reads hidden and not "File removed", and its name is never given. Search, citations, the AI's pool and shared chat answers leave it out. Counting, replacing and removing links shows a person only the links they can see; links they cannot see are kept and a remove of one is a quiet no-op. The `links` and `library` stream events are sent per viewer, to people who could see the file before the change or can after it; the event that names a holder object still reaches those who can see the holder.
  - **Shares.** Creating or changing a share checks the maker's sight of each file and refuses the whole request if one is hidden. Listing shows each person only the files they can see, and a share none of whose files they can see answers as not there, except to its maker, who can still list and turn it off.
  - **Totals.** The list's file counts, `uses` and byte total count only visible files. The quotas are enforced on the real totals, so a quota refusal and a total can show that files a person cannot see take space.
- **Turning off and uninstalling.** `GET /api/modules` carries `libraryFiles` and `libraryBytes` for a library module; the uninstall answer says `filesRemoved` or `filesKept`. The Modules page does not show them yet.

### Keeping links true

`server/object-sync.js` keeps a pointer true after its object changes, with no page open ([plan-linked-objects](../plans/plan-linked-objects.md), [plan-plan-calendar-sync](../plans/plan-plan-calendar-sync.md)). The `PUT` and `DELETE /api/modules/:id/data/:key` routes read the old value, write, and then call `afterWrite` with the old and new values, the writer and the writer's time zone (`tz`, sent by `public/module-host.js`; `TZ`, then UTC, when it is missing or unknown). `afterWrite` maps the key to a produced kind and does three things. It tells the modules that hold a link to the object (`refchange` on the module stream, tagged with its environment so that only that environment's streams hear it, and only to the frames of those modules the viewer may see, and only when the summary changed or the object went). It acts on each holder whose kind declares `holds`: removes or marks it on delete, copies the title, and moves its day with the object unless it is pinned. And it keeps dated twins: a kind with `mirror: "out"` gets one twin in each kind with `mirror: "in"` that is on in the same space and that the sender was approved to link to, and an edit on either side writes the mapped title, day and time into the other. Converting between a day and an instant uses the writer's time zone.

The server keeps the pairs, not the modules. A pair is a link entry in `server/module-links.js` with `pair: "active"` or `"detached"` (the twin was deleted, which hides it for good: the pair stays as the record, the sender is left as it was and the twin is never made again). `markPair` in `server/index.js` flags both ends on summaries: a twin says `copy: true` and `twinOf`, an original says `twins`. `set()` leaves pair entries alone, so a module's `setLinks` never removes one, and `to()` and `from()` include them, so backlinks and "Used by N." count them. The manifests declare what a kind does (`holds`, `dated`, `mirror`, `create`, checked in `cleanRefs` in `server/modules.js`), so no module names another. Loops cannot start: every write this file makes goes straight to the data store and never back through `afterWrite`, and a write happens only when a value differs. Those writes do not count toward the write limit; a full store (413) skips a twin until the next change.

A twin carries the original's span and its zone. The wall-clock sender's `dated` may name `endTime`, `minutes` and `zone` (`tripZone` in `server/object-sync.js` reads the zone the space keeps, the trip's, from a stored object of the sender; without one the writer's zone is used), and the instant receiver's `tz` field keeps the zone a timed twin was written in, so the Calendar can show a viewer elsewhere the trip's own wall time with a note ("Lisbon time"). Ticking All day on a twin never erases the original's time or end day, and `host.storage.set(key, value, { tz })` lets the Calendar name the trip's zone when it saves one. The fields are in [api-module-sdk](../api/api-module-sdk.md), "Dated twins".

On every start, `backfill()` gives a twin to each space object of a sending kind that has a day, holds no pointer and has no pair, in the server's time zone. `server/index.js` runs it once in a single-environment install and once per environment in a hosted one, as the server begins listening. Because a pair (active or detached) is the record, only the first start after a kind declares `mirror: "out"` makes anything. `tools/check-links.mjs` covers the change events, held pointers, pairs and a single-install restart, with test modules declared inside the check.

### Calendar feeds

`GET /feed/<token>.ics` in `server/index.js` gives a calendar app the objects of every kind marked `"feed": true` (with `"dated"`, checked in `cleanRefs`) as an iCalendar file written by `server/ics.js` (`readDated()` reads a stored value by its `dated` mapping, repeats included; `buildCalendar()` writes it in the server's `TZ`). The kinds are found from the manifests, so nothing names the Calendar. Three kinds of address share the route ([plan-space-calendars](../plans/plan-space-calendars.md), sections 1 and 2), each a token shown once and kept only as its SHA-256 with `made` and `readAt`:

- **A person's everything address**, `user.calendarFeed` (`store.setCalendarFeed()`, `userByFeedHash()`): every event the person may read, checked at each read (the environment's own data, and each space they are a member of, the `spaces-data` rule).
- **A person's address for one space**, `user.spaces[<space id>].calendarFeed` (`setSpaceCalendarFeed()`, `spaceFeedByHash()`, `noteSpaceCalendarFeedRead()`): that space's events only, with the person's rights there. One token per person per space, not one per space, so leaving, being removed or losing `read` ends one person's address and nobody else's.
- **The environment's published calendar**, `settings.publishedCalendarFeed` (`setPublishedCalendarFeed()`, `notePublishedCalendarRead()`, the `publishedCalendarFeed` getter): the environment's own events and every space's where the module is on, read with nobody's rights, except the Lobby and spaces stored with `publishCalendar: false` (`updateSpace()`; `true` is stored as nothing).

`findFeed(hash)` decides whose a token is, in that order: an everything address and a space address only while `calendarFeeds` is on (a space address also needs the space to exist, the person still a member, and the module on and readable for them there, `spaceAddressWhy()`), the published one only while `publishedCalendar` is on; anything else is a plain 404 that never says which test failed. `readFeed()` does the reading for all three from a list of sources (a module, its kinds, the places to read), and `feedEvents()`, `spaceFeedEvents()` and `publishedFeedEvents()` build that list; a space address leaves the space's name out of each description, since the calendar is named after the space (`X-WR-CALNAME`), and an event keeps the same `UID` in every address. `feedModule()` names the module the addresses carry, as the environment shows it, and `addressesWhy()` and `spaceAddressWhy()` give the one sentence Profile shows when an address cannot be held; `GET /api/me/calendars` answers Profile's whole Calendars tab from them.

The tokens go with the membership: `removeMember()`, an `updateSpace()` that patches `members`, and `removeSpace()` each call `dropSpaceCalendarFeed()` for everyone no longer in the space, and a deleted person's record takes both their addresses with it. Reads are limited to 30 a minute per address (`feedReads`, keyed by the environment's slug and the hash), and each address's `readAt` is written at most hourly. The routes are in [api-modules](../api/api-modules.md), "Calendar feeds"; `tools/check-feed.mjs` holds them.

### Calendar sharing's switches

Three environment settings govern calendar sharing ([plan-space-calendars](../plans/plan-space-calendars.md), decision 7): `calendarFeeds` (the everything and space addresses out), `otherCalendars` (other calendars in, and busy times when they are built) and `publishedCalendar` (the published calendar's address, above). `otherCalendars` has no default in `DEFAULT_SETTINGS` on purpose: `store.otherCalendarsOn()` in `server/store.js` answers it when set and `calendarFeeds` when not, so an environment that allowed other calendars under the one old switch still does, with nothing rewritten. Every check of other calendars in `server/index.js` (the routes, `externalAllowed()`, `externalWhy()`, the `external-events` route and the stream's `external` event) asks `otherCalendarsOn()`.

The switches are drawn by the host on the Module Configuration page (`public/module-config.html` and `.js`, `wireHostSections()`), above the module's own settings, so the host still names no module. `sharingOf()` in `server/index.js` decides which modules take part, from the manifest alone (a `"feed": true` dated kind, or the `external` hook, and `busy` once a manifest can declare it, in the running version or a newer bundled one), and answers `sharing` and `sharingReasons` on each module in `GET /api/modules`; the page shows only the switches a module has a key for, and draws a waiting one off and disabled with its reason, adding a link to the Modules tab for owners and the admin. Under the switches, while `publishedCalendar` is on, the same page draws the published calendar's state from `GET /api/settings`' `publishedCalendarFeed` and makes, replaces and turns off its address (`POST` and `DELETE /api/settings/published-calendar`), showing the address once; a space's own place in it is the **Calendar** section of `public/space-settings.html` (`#e-publish-calendar`, `PATCH /api/spaces/:id { publishCalendar }`), shown only while publishing is on and never for the Lobby. A 401 from `GET /api/modules` sends the person to sign in; a 403 says "Only owners can change this." and stops, so a member is never sent round a sign-in loop. The same page draws **Show in the top bar** for a module that declares a destination's `main` part, from `GET /api/settings`' `topBarReasons`, and calls `refreshDestinations()` after a change. `isConfigurable()` in `public/admin.js` counts both, so the Calendar's Module Configuration button is no longer disabled. Manage's environment tab keeps one line pointing to the configuration page (`#calendar-sharing-pointer`, for one release). The contract is in [api-modules](../api/api-modules.md), "Calendar feeds"; `tools/check-feed.mjs` and `tools/check-external-calendars.mjs` hold it.

### Other calendars

A person may add up to five private calendar addresses on their profile (`/api/me/external-calendars`), while `otherCalendars` is on (above). `server/external-calendars.js` (one per environment, `server/environment.js`) reads them through the private-address guard in `server/link-preview.js` (https only, 5 MB, 15 seconds; IPv6 literals and names resolving to private or special IPv6 ranges are refused, as for link previews and Research), parses them with `server/ics-read.js` (repeats expanded, 30 days back to 180 ahead, 2,000 per calendar; a file needing more than 200,000 repeat periods to expand (or, as a backstop, 1,500 ms) is refused whole as too complex), and keeps the events in memory only, reading again every 30 minutes for someone seen in 14 days and after a restart on first use. The addresses are sealed on the user record with the secrets key (`auth.encryptSecret`) and opened only to read them or show their host. A module reaches the events only through the `external` hook, which an owner approves, and only the signed-in person's own (`GET /api/modules/:id/external-events`, `host.external.events`); a read tells that person's pages with an `external` stream event. They never show inside a space: not on its canvas, a window popped out of it, a keyed page, or a page opened over a call, `/calendar` included. Nothing names a provider or a module. When it can't be used, `externalWhy()` gives the person one sentence saying why, from the switch through each way the module with the hook can fail to run; Profile's section (`public/profile.js`) reads it again on `visibilitychange` and on a `pageshow` from the back-forward cache, so an approval made in Manage shows without a reload. The contract is in [api-modules](../api/api-modules.md), "Other calendars"; `tools/check-external-calendars.mjs` holds it.

### Calendar markers

A kind marked `"marker": true` beside `"dated"` shows on a calendar as a marker that links back to its object ([plan-calendar-markers](../plans/plan-calendar-markers.md)): To-do's tasks on their due day and Polls' polls at their closing time. Markers are deliberately not twins. A twin is a real event the server writes and keeps in step; a marker is read, never written, so the Calendar does not fill up with copies and there is nothing to keep in step or clean up. That is why `cleanRefs` in `server/modules.js` refuses `marker` with `mirror` (and with `feed`, since markers never go in a calendar feed), and why it needs `dated`: `readDated()` in `server/ics.js`, which also serves the feeds, turns a stored value into a day or an instant. Its instant form takes a number of milliseconds as well as a string, so Polls' `closesAt` needed no data change.

`GET /api/modules/:id/markers` in `server/index.js` is asked by the consuming module (the Calendar), not the producer. It walks every enabled module's marker kinds and reads them in the places the mount reads: a space, or the environment and each space the viewer is a member of (the `spaces-data` rule). Each place goes through `refScope`, so the producer must be on there and readable by the viewer as they are now, and each kind through `consumerMayLink`, so the Calendar's existing approval to consume `"*"` covers it with no new hook or approval. An object whose `summary.done` field is true is left out. The route's `past` is worked out on the server, in its `TZ` for a day; the Calendar does not use it, and works out past itself in the viewer's own time, again each minute, so a marker dims as its time passes. The stream's `markers` event (`markerKindAt()` maps a written key to its kind) names the modules that may show it, and carries no data; `public/module-host.js` passes it only to those frames, which ask again. Each marker carries its module's tint (`color`) and its icon as inline SVG (`svg`), since a frame cannot load the icon font and a guest cannot ask `/api/icons`, and `due` (the kind is dated by a day, not a moment), from which the Calendar takes its words ("Tasks due", "Polls closing"). Nothing names To-do, Polls or the Calendar.

In the Calendar (`modules/calendar/src/calendar.js`) markers are kept apart from events: a separate map, drawn as a chip with `data-marker` (never `data-open`, so never edited, dragged or dropped on), opened with `host.objects.open`. The Calendar asks for the period shown with a week either side, and asks again only when the view leaves it or a `markers` event comes. The kinds it has seen become filter switches: on the environment page in its own filter row (not remembered), in a space in a toolbar menu (remembered per space in `localStorage`, `calendar-markers-off:<spaceId>`), and on the destination through `host.destination.set({ markerKinds })`, which `public/destination.js` remembers and lists in the page's filter, its choice going back as `markersOff`. The contract is in [api-modules](../api/api-modules.md), "Calendar markers"; `tools/check-markers.mjs` holds it, with test modules declared inside the check.

### Flight lookup

The Planner's **Look up a flight** fills a flight from the same flight number saved before on this server ([plan-flight-lookup](../plans/plan-flight-lookup.md), GitHub #188). No free source that allows commercial use can answer a future flight, so the server learns a schedule from what people save, and pairs it with a bundled list of airports. Nothing outside the server is asked. The routes are in [api-modules](../api/api-modules.md), "Flight lookup"; `tools/check-flight-lookup.mjs` holds the airport list and the schedule, and `tools/check-travel.mjs` the Planner's side.

- **One function.** Every lookup goes through `findFlights({ number, date, schedule })` in `server/flight-lookup.js`. Today it asks only the saved schedule. If an outside service is ever added, it goes inside this function, switched on by an environment variable holding its key; no such variable exists or is read now.
- **The declaration.** A module asks for it with `"lookups": ["flight"]` in `module.json` (`cleanLookups()` in `server/modules.js`; `flight` is the only kind). The routes are in `server/index.js` under "flight lookup, from the server", and use `moduleAccess(req, res, 'write')`, so a guest never reaches them. `flightSuggestionsOn()` reads the environment setting `suggestFlights` of every installed module (on or off) that declares the lookup and has that setting: if any has it off, the environment neither suggests nor contributes, through any module, so its travel stays its own; the choice is the environment's, not one module's. The airport lookup ignores the setting.
- **The airport list.** `server/airports.json`, every airport with an IATA code (7,918), keyed by it, each `{ icao, name, city, country, tz }`. It is built from [mwgg/Airports](https://github.com/mwgg/Airports) (MIT) by `tools/build-airports.mjs`, which pins one commit and checks the source's SHA-256, keeps only those fields, and writes the MIT notice beside it as `server/airports-LICENSE`, with the commit. To rebuild (an airport opened, a code changed): move the pin, run the tool (`--from <dir>` reads a downloaded copy instead of the network), run `check-flight-lookup`, and commit both files. `server/airports.js` reads the list once, on first use, and never writes it. It answers `airport(code)` by IATA or ICAO code, `displayName()` (the name without a trailing "International Airport" or "Airport"), and turns local clock times into moments and back with `Intl.DateTimeFormat` and no added package (`localToUtc`, `utcToLocal`, `minutesBetween`, `arrivalFrom`), so a flight time can be worked out across time zones and changes of clocks.
- **Where the schedule lives.** One file for the whole server, `flight-schedule.json` in the root `DATA_DIR`, built once at start (`new FlightSchedule(DATA_DIR)` in `server/index.js`), not per environment. On a hosted install that is the host's folder, beside `host.json`, never an environment's folder: it is not in an environment's export or backup, deleting an environment leaves it alone, and `migrateIfNeeded()` leaves it at the root when a single install becomes the first environment. On a single install the root `DATA_DIR` is the environment's, so the file sits beside its other files. It is kept in memory and written 2 seconds after a change, through a temporary file and a rename, and at shutdown. Two kinds of file are not read as a schedule. One that is not a schedule (not JSON, or without a `numbers` object) is moved aside as `flight-schedule.json.bad-<time>` (mode 600, `setAside()`) so the next write can't cover what someone may want to look at, and the schedule starts empty. One over 40 MB is left as it is and the schedule is read-only (`readOnly`, also set when moving a bad file aside fails): it starts empty, `remember()` keeps nothing and nothing is written, until the admin's **Clear all** (`clear()`) replaces the file with an empty schedule, after which it learns again; if that write fails, the route answers 500 and the file stays read-only.
- **What it holds.** For each cleaned flight number (`WN2483`), up to 5 schedules, each: `airline` (as saved with the flight), `from` and `to` (IATA codes), `departs` and `arrives` (local clock times), `days` (how many days after leaving it lands, from -1 to 7), `minutes`, `terminal` (the departure terminal), `weekdays` (the days of the week it was seen leaving, Monday 1) and `lastSeen` (the latest departure day it was saved for). Two saves with the same airports and clock times are one schedule: the day of the week is added, and a save for the same day as `lastSeen` or later moves `lastSeen` forward and brings its airline and terminal (when it has them), its day count and flight time; an older save only adds its weekday and never overwrites those. A save is kept only if it departs no more than 400 days ahead and no more than 3 years back (`MAX_DAYS_AHEAD`, `MAX_DAYS_BACK`; no airline sells further out, and either would rank first, or never go, for years). Past 5 schedules for a number, the one seen least recently goes; past 20,000 numbers, likewise. Every schedule is rebuilt from these fields alone by `cleanSchedule()`, on the way in, when the file is read and when it is written, so nothing else can be written back; when the file is read, a `lastSeen` further ahead than 400 days is clamped to that day and one older than 3 years drops the schedule.
- **What it never holds:** who saved it, which environment or space it came from, anyone's name, the seat, class, booking reference, cost, who paid, the people on it, the notes, the title or the gate. The Planner sends only the schedule part (`flightObject()` in `modules/travel/src/travel-lib-object.js`: the airline, the cleaned number, both airport codes without their typed names, the departure, the arrival on the ticket, the flight time and the terminal, under a fixed title), and the server reads only the fields above out of that. An answer gives `lastSeen` as a month only.
- **Clearing.** The admin sees the counts and can forget one number or clear everything: on a hosted server from the host console's Host tab (`/api/host/flight-schedule`), on a single install from Manage's Modules tab (`/api/flight-schedule`). Both pages draw the same **Flight schedule** section with `wireFlightSchedule(route)` in `public/flight-schedule.js`. An environment's owner on a hosted server can't clear what other environments taught.

### The Planner's phases, width and drag

These are the parts of the Planner (`modules/travel/`) that other code or checks depend on.

- **Unscheduled is a default phase.** `phaseOf(item, bands)` in `travel-lib.js` returns the object's own `phase` when the space lists it, else `null`; it takes no date and never falls back to today's phase. The Unscheduled area (`travel.js`) draws an "Unscheduled" group first for the objects whose `phaseOf` is `null` (no phase, or a stored phase that is no longer listed). `undatedItems()` also includes an object whose date the plan cannot show (outside the plan); it is grouped by `phaseOf` like the rest, so it is under Unscheduled unless it has a listed phase of its own, then one group per real phase; with no phases the list is flat. It is not a phase bar, not in the date strip and not in the phase settings. The object editor's `f-phase` select lists "Unscheduled" first (value empty) and starts on it; saving it stores no phase. The Calendar's phase tints and the status strip are unchanged.
- **The narrow layout is keyed on the pane, not the window.** `travel.js` sets `.app.narrow` when the pane is under 720px wide and `.app.tiny` under 480px (720px stays the threshold: the module's own width decides, so a small window, a docked column and a phone behave the same, and a tablet held upright gets the narrow layout), and `travel.css` repeats the narrow-layout rules of `system.css` on those classes: 44px targets (the hit area grows past the box by `--btn-hit`), and the day's Add button keeps only its plus. A day card is a size container, and under 300px wide (a docked 256px column) the day head becomes a grid: date, title and actions on the first row, the summary and the tag under the title.
- **The time column** is built in `travel.js` from the object's start (`tt`, the environment's clock), its end (`endText`, `→ 9:30 PM`, with ` +1` past midnight) and its length (`lengthText`, `(1 h 30 min)`), one per line, each left out when it is missing; in the narrow layout the lines run together above the card. The joint between two days and its + are centred on the gap; a phase bar (`buildPhaseMarker`, `.row.marker.phase`) spans the days' column at 32px high, with `flag` for a start or `flag-checkered` for an end, the "<phase> starts" or "<phase> ends" label and the date at its end.
- **Drag scrolls at the edges.** While an object is dragged, `dragover` feeds the pointer's height to an edge scroller: inside a zone of 56px (or 15% of the list, if smaller) at the top or bottom of the list's visible area the list scrolls, faster the nearer or further past the edge, at most 20px a frame and 6px with `prefers-reduced-motion`. It stops when the pointer leaves the zone or the window, at the end of the list, on drop, on `dragend` and on Escape. Dragging never sets `scrollTop` to a fixed value, so the list does not jump when a drag starts.
- **The Prototype page runs this code.** The Prototype's Planner section loads the Planner's own markup and stylesheets (`public/design-system/sources.js`, `prototype-planner.js`), and `tools/check-prototype-parity.mjs` holds the two together (see [design-theme](../designsystem/design-theme.md), "The design system pages").

### The objects format

An AI writes objects in one fixed shape, whether it is the Assistant's own AI or another AI a person researched in, and one checker reads both. `server/object-format.js` owns that shape: the icons and kinds, the field caps (title 80, content 6000, five tags, five `http` or `https` links), `cleanObject` (the checker), `objectRule` (the prompt text), `instructions` (the text a person gives another AI), `schema` (a JSON schema) and `readObjects` (finding objects in a paste or a file). `server/ai.js` takes its icons, kinds, checker and rule from there: its `summaryRule(kinds)` (the rule for `/ai`'s answers) is `objectRule` called with the `objects` fence, the noun "object" and a limit of 20, and the published instructions are the same function called with the same fence, this environment's word for object and a limit of 50, so the two cannot drift. The only differences are deliberate: `/ai` explains `basis` and `sources`, and, since it can't stop to ask, says which dates it still needs where the copied instructions tell the AI to ask the person. `parseSummaries` reads blocks labelled `objects` and, for a model that labels its block loosely, `summary`, `json` or nothing. `tools/check-object-format.mjs` checks that both ask for one array in one `objects` block and that the rule never says "card".

**Kinds and details.** The kinds belong to the format, not to any module: `TRAVEL_KINDS` (the 13 from before) plus `event`, `task`, `poll`, `note` and `link` make `KINDS`, and `HANDOFF_KINDS` (`image`) is kept only when `cleanObject` is called with `handoff`, which no import or AI answer is. Each kind may carry `details`, its own typed fields, listed once in `DETAILS`; `cleanDetails` reads them field by field and drops what doesn't fit, so one bad value never costs the object, and `schema()` builds its `details-<kind>` definitions from the same table. Times are local clock times with no zone, because a flight's 12:50 departure is 12:50 wherever the reader is; a zone an AI adds is dropped rather than converted. The format stays version 1, since every older object is still valid. These are steps 1 to 3 of [plan-object-handoff](../plans/plan-object-handoff.md); the Planner reading `details` into its own fields is step 5, and Research, To-do, Calendar and Polls doing the same are steps 6 and 7. Chat's **Keep** chooses its keeper with `keeperFor` in `public/chat-input.js`, which sends only a travel kind to the typed keeper (`acceptSuggestion`); its copy of `TRAVEL_KINDS` is held equal to the server's by `tools/check-chat-page.mjs`. What it sends follows the keeper's `takes` (`objectInputOf`, the same rule as the server's `takersOf`): the object itself to a keeper that takes its kind, the older flat fields with the details as "Label: value" lines to one that doesn't. The fields are in [api-modules](../api/api-modules.md), "The objects format".

**What modules take, and the prompt that follows.** A module says which objects an action accepts with `takes` on the action (`cleanTakes` in `server/modules.js`): catalogue kinds, `"*"` (any object, with `except` to leave kinds out) or `"text"` (a message's words, an object with no kind), the words for "Add to <module> as ...", and optionally one of the module's own permissions. The kinds are the format's, so two modules never invent clashing words for a flight, and the server still names no module: Chat and the import will find targets by `takes`, not by an action's name. `except` exists for the Calendar, which takes any dated object but not the travel kinds, since those reach it through the Planner (plan decision 19); it was the plan's open question, settled in step 2. `"*"` never covers `image`, because a picture is only useful to a module that keeps uploads, which must name it.

The prompt is built from the same declarations. `kindsTaken` in `server/object-format.js` collects the kinds the enabled modules' `takes` name, in the catalogue's order, and `promptKinds()` in `server/index.js` hands them to both the copied instructions (`GET /api/objects/format`) and `ai.run` for `/ai`; `objectRule` then writes one details line per listed kind from `DETAILS`. So the instructions ask only for what something here can keep, and turning a module off takes its kinds out. While an enabled module still offers the older typed keeper (`acceptSuggestion` taking a `title` and a `kind`, with no `takes`), the 13 travel kinds are listed as before, so an environment with an older Planner loses nothing. The rules the prompt gives the AI (one object per leg of an itinerary, copy dates and never guess them, local 24-hour times with no zone) come from #182, where an undated, unstructured flight looked like a broken import. The exact text is in [api-modules](../api/api-modules.md), "The instructions". With the bundled modules today the prompt lists every kind: the Planner, Research, To-do, the Calendar and Polls all declare `takes` (steps 5 to 7).

**Mapping into a module's own fields.** Each module maps an `object` input in its own code, with three shared helpers in the SDK rather than a copy in each module: `host.util.plain` (Markdown and HTML to plain text, for every field shown as plain text), `host.util.localWhen` (a `when` to a local `{ date, time }`, a zone dropped and the clock kept) and `host.util.detailLines` (the details a module has no place for as "Label: value" lines, in one set of words), all in `public/sdk/host.js` and also on `window.hostText`. So nothing is lost, and the same flight reads the same in a Research note, a task's notes or an event's description. Each module's mapping is a library file with no page in it, so a check runs it with the SDK's real helpers: `objectNote` and `objectLink` in Research's `research-lib.js` (`tools/check-research.mjs`), `taskFromObject` in To-do's `todo-lib.js`, `eventFromObject` in the Calendar's `calendar-lib.js` and `pollFromObject` in Polls' `polls-lib.js` (`tools/check-object-handoff.mjs`). Polls' `draftPoll` only fills the form, since a poll is a question a person should word. The Calendar takes any dated object but the travel kinds (one `takes` entry with `except`) and says `needs: ["date"]`, so menus and To-do's rules offer it only for something with a day; a timed start is read in the zone of the browser that carries the request out, because events have no zones (a plan of its own). The Planner's mapping is `objectFields` in `modules/travel/src/travel-lib-object.js`, a file with no page in it so `tools/check-travel.mjs` runs it with the SDK's real helpers. Two Planner decisions come with it: a journey keeps its arrival as on the ticket (`arrives`, beside `minutes`), because a flight across zones has both a clock arrival and a time in the air that can't be worked from each other without zones; and an object handed in dated beyond the plan's 60 days goes under "Unscheduled" with its date in its notes and a note to the person (`addHandedIn` in `travel-lib-plan.js`), where before it was saved on a day the plan could not show. The contract is in [api-modules](../api/api-modules.md), "The Planner's acceptSuggestion".

**Named by kind.** The file is `<something>.objects.json`, `{ "format": "objects", "formatVersion": 1, "objects": [...] }`, and the block is fenced ```` ```objects ````. The theme and template files carry the same marker pair with their own kind (see [architecture-overview](architecture-overview.md), "Themes", and [architecture-environments](architecture-environments.md), "Template files"). `server/file-format.js` is the one rule for all three: `stamp(kind)` writes the pair, and `readMarker(file, kind)` answers `ok`, `newer`, `old` or `not`, so no reader repeats it. Until 2026-09-30 the formats were named after the product; Thomas decided they are named by kind so the product's name can change without touching a format ([plan-kind-names](../plans/plan-kind-names.md)). Old files and answers are refused with a sentence saying what to do, never read: an old marker is recognised by its exact past name, built from `PAST_BLOCK_LABELS` (the two labels ever published) and the kind, so a real object with a key such as `relatedObjects` is still an object; and a paste with a block fenced with a past label, wherever the fence line sits (indented, in a list or a quote), is refused whole, even beside an `objects` block, so nothing is imported by halves. `PAST_BLOCK_LABELS` is the only place the old labels are written in the code and must never grow. The loose reading (any JSON object with a `title`) still rescues a paste that lost its fences, and is the only way a ```` ```card ```` block is read now. The exact rules are in [api-modules](../api/api-modules.md), "The objects format".

Reading costs no AI and stores nothing, so it is a conduit, not an AI feature. `GET /api/objects/format` and `/format/schema` publish the format to anyone signed in or holding a guest link. `GET` and `POST /api/modules/:id/objects/check` answer, for the asking module in its place, whether this person may bring objects in and what a paste or file holds. The rule is the module's own `write` permission, never a guest (a space with AI turned off does not matter: a paste is not AI use); no AI service, `useAi` or new module permission, because a new permission would turn the module off on every install until an owner approved it again, and what is finally kept is limited anyway by the destination module's own write permission, since keeping goes through actions. The route has its own body parsers (`text/plain`, or `application/octet-stream` decoded as `public/file-text.js` does) with a 256 KB cap and its own 413 branch in the error handler, and a `check` rate limit of 20 a minute in `server/module-limits.js`. An object read this way is always marked `basis: "imported"` and loses its `sources`, since another AI's item numbers mean nothing here. The contract is in [api-modules](../api/api-modules.md), "The objects format".

Nothing here keeps an object. A module that brings objects in decides where they go; the Assistant, the only one today, keeps them through the action bus exactly as it keeps its own answers (a suggestion-shaped action for an object with a `kind`, else a note-shaped one), which reaches Research and the Planner. So long research fits, a `text` action input is kept up to 8000 characters (it was 1000), and the Planner keeps notes up to 8000. Choosing among more destinations (To-do, Calendar, Polls) by their `takes` is planned in [plan-object-handoff](../plans/plan-object-handoff.md), and a direct connection for AI apps after #64 in [plan-research-import](../plans/plan-research-import.md).

### Events and actions

`server/module-bus.js` keeps the two other conduits. An **event** (`POST /api/bus/publish`) must be one the publishing module declared, from a person who can write to that module in that place, with an optional pointer that can only be to the module's own objects there; it is stored (500 kept, 14 days) and announced on the shared stream (`GET /api/modules/stream`) as a `bus` event that names the modules that may hear it: those that declared and were approved for it and that this viewer can see in that place. The host delivers it only to those frames. A subscriber that was not open catches up from a cursor the SDK keeps in the module's own data (`GET /api/bus/events?after=`); a module hears nothing from before its first subscribe. An **action** (`POST /api/bus/actions/request`) is checked in the order asking module approved for it, the person can do the thing themselves (write access to the provider), the provider declared it; its input is validated against the declared field types (a `string` cut at 200 characters, a `text` at 8000) and only those fields are stored, then it waits in the provider's queue. The provider's frames are told (`action` on the stream); each asks to `claim` it and only one is given it (a claim not completed within a minute can be taken again), carries it out under the rules of whoever has the module open, and reports `complete`. Modules run no code here, so a request with no provider page open simply waits (seven days) for a person to open one. Two exceptions come with Chat's **Send to...** (plan-object-handoff step 9). A request made with `openOnly` (Chat's `/action` asking a `local` action, a form on the person's own open page) carries `expiresAt`, 60 seconds on: past it, unclaimed, `pending` and `claim` no longer hand it out and `statusOf` reports `expired`, because a form opening minutes later on a page the person has left would be a surprise. And a request records `doneAt` when it completes, so `GET /api/spaces/:id/action/:requestId` can tell the person how it went for 10 minutes (`BUS_LIMITS.resultMs`). `prune` returns the requests it drops that were never carried out (aged out, pushed past the cap, or expired and past the result window), and `pruneAndSave` emits them as `actionsDropped`; `server/environment.js` listens and removes a picture uploaded for such a request (the upload sweep: only the asker's own upload in the request's place, and only when the module's data doesn't name it), noting it in the activity list. The bus itself still knows nothing of pictures. **Actions in the object's own place.** An environment page (a destination's part) may ask for an action on one of the provider's own objects in a space, such as setting a space's task's due date from Calendar. The request is checked by the viewer's right to change the provider in that object's space, not at environment level (`actionObjectSpace()` and `takesOwnObject()` in `server/index.js`, for an action whose input takes a `ref:<provider>:<kind>`); it still waits at environment level, where the asking and providing parts are, and records the space (`space` on the request in `module-bus.js`), so `pending`, `claim` and `complete` let only someone who may change the provider there take it. `GET /api/bus/actions?ref=` lists the actions by the same rule for the object a drop is about. A page in a space keeps its own place, as before. Nothing in `module-bus.js` or its routes knows what an event or an action means. An `object` input field carries a whole object in the objects format: `busInput` cleans it with `cleanHandoff` (the format's own checker, keeping a picture's `image` kind), so a module receives exactly what an import would keep, and refuses a kind the action's `takes` doesn't cover, or one whose entries all need a permission the person lacks (`takerOf` and `takesFor` in `server/index.js`). Every route that requests an action (`/api/bus/actions/request`, and Chat's `/action` and `/command`) answers such a refusal with its own status and sentence, and a body over 64 KB with 413. `GET /api/spaces/:id/actions` and `GET /api/bus/actions` return `takes` with a `may` per entry; the first lists an action nobody here may use with `may: false`, the second leaves it out. A `ref` input field can be typed `ref:module:kind` (checked in `cleanBus` and enforced in `busInput`), and `GET /api/bus/actions?accepts=module:kind` lists the actions that take that kind, which is how a module receiving a drop learns what can be done with the object without knowing where it came from. Events may declare the data they carry (`cleanBus` keeps up to six typed fields), and `GET /api/objects/kinds` lists, for each kind a module may link to, the events that kind reports and their data; that is how a following module offers rules without naming the module it follows. The drop menu is drawn by the SDK (`host.actions.pick`) inside the module's own root, at the point of the drop, so it works the same in a frame and in the page; the choices are the receiving module's own plus the actions Chameleon lists, filled from what the receiver has.

### Commands

`cleanCommands` in `server/modules.js` checks a manifest's `commands` against its own `actions.provides` (each must name a `local` action that takes `text`; `ai` is reserved), at install and again when the registry loads. `GET /api/modules/for-space` hands them to the page, and `POST /api/spaces/:id/command` in `server/index.js` finds the one named and requests its action on the bus, so Chat never names a module. The contract is in [api-modules](../api/api-modules.md); the reasons in [plan-one-input](../plans/plan-one-input.md).

### Hooks

`server/module-hooks.js` holds schedules and notifications. Schedules persist to `data/modules/schedules.json` and a ten-second timer fires what is due: it delivers the schedule's notification, if any, and emits `fire`. A schedule more than six hours late (the server was off) is dropped. The timer's tick runs inside its environment (`runIn`, which `server/index.js` sets to that environment's context), and each listener of `fire` and `notification` is called on its own (`tell()`): one that throws is logged, the rest still hear, and nothing stored is undone, so a schedule can never stop the server. A notification is stored before listeners are told. The stream routes register their listeners with `listenIn()`, so an event from the timer, or from a region cut, is handled in the listener's own environment. `tools/check-hooks.mjs` holds this. A repeating schedule is put back for its next time as it fires (`requeue`), computed in the schedule's time zone with `Intl` so the wall-clock time survives daylight saving changes; it skips times the server slept through and stops after `until`. Notifications persist per person in `notifications.json`, capped at 50, and are emitted as `notification` events on `GET /api/notifications/stream`. A notification reaches only people who pass the module's `read` permission for that place, which `resolveRecipients` in `server/index.js` checks. A schedule set by the module while an admin approved the hook is the only way a module causes anything to happen on its own.

### Where modules show

- **Environment pages.** A module's environment page is reached from its tile's heading on home, or at `/modules/<id>`; the top bar has no entry for module pages (plan-primary-nav, decisions 30 and 31). Opened from the space page they open in the in-page overlay, so the call keeps running.
- **Environment page.** `/modules/<id>` serves `public/module.html`, whose script (`public/module.js`) mounts the module in a full-height frame.
- **Destinations.** A destination is a host page of its own in the top bar (Calendar at `/calendar`, Map at `/map`), made of the parts modules declare in `surfaces.destination`: one `main` and any number of panels per destination, each an entry of the module's own, mounted at environment scope ([plan-calendar-destination](../plans/plan-calendar-destination.md), [plan-map-destination](../plans/plan-map-destination.md)). The host names the destinations, never the modules: `server/destinations.js` holds the list (`DESTINATIONS`: id, the environment option that shows it, its page, and whether it needs its main module to have a file), picks the `main` (the bundled module that declares it, else the first by id), orders the panels and decides who sees what; `cleanDestinationParts()` in `server/modules.js` checks the manifest field (a destination the host knows, at most one `main` and one `panel` per destination, two parts in all, the `environment` scope). So the Calendar is a destination because the Calendar module declares its `main`, and a module written later can offer a panel with no change to Chameleon. While a destination is shown, the environment page of each module that is part of it redirects there and its tile's heading leads there (`destinationPathOf()` in `server/index.js`). The page and its state are in [architecture-navigation](architecture-navigation.md), "Destinations"; the routes in [api-modules](../api/api-modules.md), "Destinations".
- **Modules on the canvas.** `public/canvas.js` drives the Layout button in the space bar and its panel's Show section (the menu lists the conference, the chat and the modules, opens under the button, and is the single way to open or close a module (when the menu element carries the class `subnav-modules`, it is an always-visible row of buttons in the space bar: `public/canvas.js` then never hides or positions it and only keeps its buttons current); the chat's unread count shows on the button) and opens each module in one of three ways. **Docked**: a column of the canvas's grid after the video and the chat (see [architecture-canvas](architecture-canvas.md)), with a header the host draws at the shared height and a drag handle on its left edge. **Floating**: in a layer on the main page, dragged by its title and resized by its corner. **Popped out**: its own window, which is `/modules/<id>?space=<space id>&popout=1` (the same page an environment page uses, in the space's scope, with no header; the old `?moduleRoom=` answers 301 to it). A module's manifest says whether it supports docked and floating; the choice, the docked width and the floating box are remembered per module in `localStorage`. When the whole call is popped out, the modules follow it into the popup window (each module is opened again there, because a frame moved between windows would reload). A space's modules come from `/api/modules/for-space` and are turned on per space from the space's own settings. The page reads that list on entering the space and again on each `modules` event of the notifications stream (`brand.js` raises `app:modules-changed`, also after the stream reconnects; `reread()` in `public/canvas.js` redraws the Show list, tabs and menu and closes an open module that is no longer on), so a module turned on or off shows or leaves without a refresh; one whose `surfaces.canvas.menu` is `false` is left out of the menu and never opened or restored (the Assistant).
- **The Lobby** (plan-modules, "the Lobby is for being together", GitHub #63). The Lobby is social: chat, the conference, and modules whose manifest declares `surfaces.canvas.lobby: true` (the Calendar, from 1.17.15). `ModuleManager.onInSpace()` and `modules.isOnIn(id, spaceId)` in `server/modules.js` are the one check for whether a module is on in a space (`allSpaces` or `spaces`, and the Lobby only with the field); `moduleSpaceAccess()`, the reads across spaces, a space's module settings and the live change stream all use it. `allSpaces` keeps its stored meaning, "every space this module may be in". `modules.lobbySync()` runs after each environment build's bundled updates, and after a rollback, and takes `lobby` out of `spaces` for any module whose active version doesn't declare the field; its Lobby data is kept. The refusals and their sentence are in [api-modules](../api/api-modules.md). On the pages, Manage's "Available in every space" carries "(not in <Lobby>)" for such a module, and the Lobby's own settings page lists only modules made for it (`public/space-settings.js`).
- **A module's colour.** A manifest may name one of the theme's eight tints in `color` (`cleanColor()` in `server/modules.js`; [api-modules](../api/api-modules.md)). The host draws it, never the module: `data-tint` on the module's icon in its titlebar and its line in the Layout menu's Show section, and on its messages in Chat, where CSS turns it into `--tint` ([design-theme](../designsystem/design-theme.md), "Tints"). The AI is gold. The tint tokens also reach every module page, in `/sdk/host.css` and with the theme the host hands a frame, so a module can use them too. Bundled: Research blue, To-do green, Calendar red, the Planner teal, Polls purple, Places orange, Maps pink.
- **The budget target and the Budget module** ([plan-budget-module](../plans/plan-budget-module.md)). The target is a field on the space record (`budget`, `budgetOf()` and `budgetProblem()` in `server/store.js`), not Budget's data, so the status strip's fact and any other module read the same one. It is left out of the general views of a space (`shownSpace()`, `withoutBudget()` in `server/index.js`) and reaches a member only through `GET /api/modules/:id/context`; those who edit it (owners, the admin, and that space's moderators, `moderates()`) also read it from `GET /api/spaces/:id` and their own `PATCH`'s answer (`answeredSpace()`). `MODERATOR_SPACE_FIELDS` includes `budget`. The manifest flag `"budget": true` (`cleanManifest()`, set again on load as `manifest.budget`) is how the host knows which module may ask: `module.js` and `mountModule` pass it to the host (`module.budget`), and `host.budget.can()` and `.set()` (`'budget.can'` and `'budget.set'` in `public/module-host.js`) refuse without it. `set()` sends one `PATCH` with only `budget`, then tells the other modules on the page (`tellSpace()`), other windows (`app:phases` and its broadcast channel) and Set up. The module itself is `modules/budget/`: `src/budget-lib.js` is pure (cents, totals, categories, settle-up, burndown, the fact's words, the host's rules for the target), is inlined into the page at `/*__LIB__*/` and is run by `tools/check-budget.mjs`; `budget.js` draws it; its costs are `cost:<id>` in the module's space storage. It reports a `spent` fact marked `budget: true` through `host.facts`, provides the `addCost` action, and produces the `cost` kind (its summary names `amount`, which the server's `SUMMARY_FIELDS` does not carry yet).
- **Notifications.** `public/brand.js` also opens the notification stream on each page (not in overlay pages, which read the counts once and leave the stream to the page underneath), shows a toast per notification, and keeps the unread counts on the top bar's bell, the home tiles and the space bar's Layout button. The bell's list shows the notices and marks them read (see [architecture-navigation](architecture-navigation.md), "The bell").

### Uninstall

Uninstalling removes the versions and the registry entry. With the data deleted too, it also forgets the module's schedules and notifications and drops its cached data.
